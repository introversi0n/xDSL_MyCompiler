# 总方案

下文路径均相对项目根目录，项目可以放在任意操作系统的任意目录中。

这是一个**持续演进的编译器学习项目**，不是以功能覆盖率衡量的通用编译器产品。用 Python + xDSL 学习 MLIR：先能读、改、打印 IR，再逐步 Lower、执行，最后接入 ONNX。每个知识点都有输入样例、可修改代码和说明。代码从简，目录用到才建。

保留理解权（能对应到 MLIR 机制）、动手空间（示例之外有习题）、可追溯性（每一步都有说明和验证）。习题预留部分是公开教材内容，不表示项目存在未交付功能。代码和命令采用跨平台 Python；C++ 只作原理与接口对照，不作为实现或构建任务。

参考 MLIR 的 `mlir-opt` / `mlir-translate` / runner 分工，但只建立实际需要的工具。新阶段尽量给已有工具增加 Dialect、Pass 或输入，不每阶段复制一个完整 opt。

### Python 包与 C++ 目录不是两份编译器

后续 Python 实现放在 `xdsl_mycompiler/`，不再用 `lib/` 作为 Python 包。stage 1 继续使用自包含脚本，不迁移代码、不提前创建空包。已有 include/lib 不承担项目实现；C++ 的目录树仅在文档中对照解释，无需为其建立源文件。

| Python/xDSL（按需创建） | C++/MLIR 常见对应位置 | 区别 |
|---|---|---|
| `xdsl_mycompiler/context.py` | 工具入口、DialectRegistry、Pass 注册代码 | 统一注册在需要复用时才抽出 |
| `xdsl_mycompiler/dialects/learn.py`、`dnnx.py` | `include/<项目>/Dialect/*/IR/*.td,*.h` 与 `lib/Dialect/*/IR/*.cpp` | IRDL 类直接参与运行；ODS 生成代码后还要编译/链接 |
| `xdsl_mycompiler/passes/*` | `include/<项目>/Transforms/Passes.h,Passes.td`、`lib/Transforms/*.cpp`，或方言自身的 Transforms | Python ModulePass 定义和实现通常同文件；C++ 可有工厂声明、实现及注册代码 |
| `xdsl_mycompiler/lowerings/*` | `include/<项目>/Conversion/*`、`lib/Conversion/*` | 转换也是 Pass；同一 lowering 不在 passes/ 和 lowerings/ 复制两份 |
| `xdsl_mycompiler/analysis/*` | `include/<项目>/Analysis/*` 与 `lib/Analysis/*` | C++ 声明/定义分离与分析管理不等同 Python 模块 |
| `xdsl_mycompiler/frontend/*`、`runtime/*` | 对应项目的前端与运行时目录 | xDSL 原生 Python IR 不需要先构建 C API/Python binding |
| `xdsl_mycompiler/utils/*` | Support/Utils 等 | 只有确实复用的小功能才抽取，不建杂物目录 |

Python 也需要依赖和模块导入管理，但通常不需要用户为自己的 .py 编译目标文件或链接 MLIR 库。C++ 不强制每个类都有独立 .h/.cpp，也不是每个 Pass 都必须写 .td：这里学习的是 MLIR 项目常用组织方式。

在 stage 3/4 必须把**同一个 op/Pass**并排讲清楚：Python 定义在哪、怎么导入/注册；C++ 声明、ODS、实现、生成文件分别在哪，哪些 CMake 目标先生成、哪些目标编译/链接。不能仅列一张类名对照表，也不要求维护另一份完整 C++ 编译器。

## stage 1：最小 my-opt

涉及：`tools/my_opt.py`、`tools/exercises/stage01_context.py`、`test/E2E/mlir/stage01/*`、`docs/stage-01-my-opt.md`。运行命令直接放在阶段文档。

1. Context → builtin/func/arith 注册 → Parser → verify → Printer。
2. 显式注册 `cse`、`dce`、`canonicalize`，按参数顺序执行，每次执行后 verify。
3. 支持输出文件和 Pass 后打印，错误返回非零退出码。
4. 示例分别展示空 module、加法、重复表达式、死代码与常量折叠。
5. 用户练习：补 Context/注册，添加 Pass，分析缺注册与错误 IR。

MLIR/C++：工具入口、MLIRContext、DialectRegistry、PassManager；学习编译、链接与运行时注册不是一回事。先不引入插件系统、包安装配置和复杂 CLI。

验收：解析打印可往返，三个 Pass 的变化能解释，错误不能被误报为成功。本阶段的常量折叠不是后端执行。

## stage 2：读更多标准 Dialect，查看结构与数据流

涉及：`tools/my_opt.py`、`tools/inspect_ir.py`、`test/E2E/mlir/stage02/*`。

1. 按样例需要注册现有 scf/cf/tensor/linalg/memref，不自己复制其定义。
2. 从直线代码、嵌套循环到多个 block，显示 op/region/block 树。
3. 单独显示 block.args、operands、results、owner、Use(operation,index)。
4. 用 `%i * %i` 展示一个值在同一 op 的两个使用槽位，不按 op.name 去重。

MLIR/C++：`mlir/IR` 的 Operation/Region/Block/Value/OpOperand、指针与值包装对象。

验收：能定位每个值的定义和使用；区分结构归属与数据依赖。注册支持解析不等于支持执行；first_use 是链表表头，不是执行顺序上的最早使用。

## stage 3：自己写 Pass，用到时再定义 Dialect

涉及：`xdsl_mycompiler/passes/*`、`xdsl_mycompiler/dialects/learn.py`、`tools/my_opt.py`、`test/E2E/mlir/stage03/*`。

1. 先对标准整数 arith 写小 pattern，例如合法的 x+0 替换；提供正例与反例。

验收：一个自定义 op 可注册/解析/验证/打印，一个 Pass 有明确条件；IRDL 与 ODS 对照说明相同语义。不是复制完整 Toy 项目，也不宣称编号对应官方 Toy 章节。

## stage 4：Lower 到 arith 与 linalg

涉及：`xdsl_mycompiler/dialects/learn.py`、`xdsl_mycompiler/lowerings/*`、`tools/my_opt.py`、`test/E2E/mlir/stage04/*`。

1. 标量 learn op → 同类型 arith，先不引入类型变化。
2. 检查源 op 残留、结果数量、类型和 uses。
3. 静态小矩阵 → linalg；解释 generic 的 inputs/outs、indexing_maps、iterator_types、body 参数、yield。
4. 对比 named matmul 与 generic，区分 tensor 结果与 memref outs。

MLIR/C++：Conversion 目录、OpConversionPattern、TypeConverter、ConversionTarget。xDSL 0.71 的局部重写/TypeConversionPattern 不等于完整 DialectConversion；需显式管理有限范围转换与合法性检查。

验收：源 op 按预期消失，输出可验证，每步 IR 都能保存。cast reconciliation 不能补齐未实现的转换；广播能否恢复循环范围需检查全部 indexing maps，不能一概断言失败。

## stage 5：执行并比较输入输出

涉及：`tools/run_ir.py`、`tools/my_opt.py`、`xdsl_mycompiler/lowerings/*`、必要时 `xdsl_mycompiler/runtime/*`、`test/E2E/mlir/stage05/*`。

1. 执行 func+arith 的 add(1,2)，检查为 3，期望写成 4 时必须失败。
2. 学 memref.alloc/load/store/dealloc 与数据所有权。
3. 对静态、直线、无别名的小 tensor 程序显式分配缓冲区，先不做复用。
4. 矩阵使用调用者提供的输出缓冲区，lowering 明确初始化 reduction 累加输出。
5. memref 语义的 linalg → scf/memref/arith → xDSL Interpreter。

MLIR/C++：LinalgToLoops、Bufferization、ExecutionEngine、MemRef descriptor 与 ABI。受限转换不是通用 One-Shot Bufferize，Python ShapedArray 不是 C++ ABI descriptor。

验收：实际执行生成 IR，标量与小矩阵结果通过，错误期望非零退出，初始化和释放时机明确。此时完成第一个小而完整的流程。

## 执行与验证合同

### 第一条路线：Python 驱动 xDSL Interpreter

```text
run_ir.py → 按函数签名准备参数 → Interpreter.call_op
          → 提取实际输出 → 比较期望 → PASS/FAIL + 退出码
```

使用已有 Interpreter/register_implementations/call_op；ShapedArray 的存储构造以实际版本验证。不另造复杂 runtime。它在 CPU 上解释执行，不是 LLVM 编译的原生机器码，计时也必须标明解释器耗时。

计划标量接口：

```text
python tools/run_ir.py add.mlir --function add --args 1 2 --expect 3
```

矩阵接口计划为 `run_ir.py program.mlir --case case.json`。JSON 写清入口、dtype、shape、data 和期望；输出缓冲区由调用者提供。整数精确比较，浮点按案例声明 atol/rtol 比较，报告形状/类型不匹配与首个差异。

memref 只表示内存；完整执行 IR 还包含 func/scf/arith 等。Dialect 注册不保证解释器支持每个 op，新增例子都需核对。

### 最终模型：用户的头文件

已有 `test/E2E/resnet50/resnet50.onnx`、`resnet50_input.h`、`resnet50_output.h`。头文件是含负数的 `const char[1024]` 输入、`const char[10]` 输出，模型真实类型/shape/layout/量化尚待核对，不能凭文件名假定标准浮点 ResNet50。

1. 查模型输入输出、opset、domain、自定义/量化算子。
2. 核对头文件长度、元素位宽、shape 乘积、预处理和布局。
3. 同目录 case.json 引用头文件并记录解释规则，不复制大数组。
4. 受限读取器只解析当前整数数组初始化格式，不用 eval、不实现通用 C++ parser。保留 8 位位模式，再按确认后的类型解释，不能依赖普通 char 的平台符号性。
5. 编译并实际执行生成的 IR，与用户输出逐元素比较；整数默认精确相等。
6. ONNX Runtime/NumPy 可以作为额外参考，不能代替本项目执行或覆盖用户期望。

### 与 MLIR 的对应边界

IR 结构概念相近；Pass/Builder/Rewrite API 不完全一样；完整 DialectConversion、AnalysisManager、通用 One-Shot Bufferize 在本版本无直接等价实现。每阶段注明本项目补了什么以及范围。文本 IR 交给 C++ MLIR 时还需版本与 Dialect 注册匹配。

原生执行作为后续独立扩展：输出标准 MLIR → 匹配版本的 MLIR 工具 → LLVM/CPU runtime。此时再学习真实 descriptor、链接库与 ABI，不把 ShapedArray 直接当成 C++ 指针。
